## Правила работы с Git

### Правила формирования коммитов

Один коммит должен содержать одно логически завершённое изменение.

Не следует объединять в один коммит несвязанные изменения

Сообщение коммита должно кратко объяснять, какое смысловое изменение было внесено.

В репозитории используется **русский язык сообщений коммитов**.

Для сообщений используется следующий формат:

`<тип>: <краткое описание изменения>`

Используемые типы:

- `feat` — добавление новых требований или разделов;
- `docs` — уточнение или дополнение документации;
- `fix` — исправление ошибки или противоречия в требованиях;
- `refactor` — изменение структуры документа без изменения смысла;
- `chore` — технические изменения структуры репозитория.

Примеры допустимых сообщений:

```text
feat: добавлены требования к отображению помещений
docs: уточнены цели заинтересованных сторон
fix: устранено противоречие в правилах отображения площади
refactor: переработана структура раздела границ проекта
chore: добавлена структура файлов варианта BI Case
```

Недопустимые сообщения:

```text
update
fix
правки
изменения
готово
asdf
```

Не допускается накопление большого количества несвязанных изменений в одном коммите.

## Работа с ветками

Основная ветка проекта:

`main`

Прямые изменения в `main` не выполняются.

Для работы создаются отдельные feature-ветки:

```text
feature/<название-задачи>
```

Например:

```text
feature/stakeholders
feature/project-scope
feature/functional-requirements
feature/rtm
```

Рабочий процесс:

```text
feature-ветка
      ↓
Pull Request
      ↓
ревью другого участника команды
      ↓
исправление замечаний
      ↓
заполнение файла review_log.md
      ↓
Approve
      ↓
слияние в main
```

Замечания, полученные во время ревью, фиксируются в файле:

`variants/BI-Case/review_log.md`

## Ревью изменений

Изменения в основной ветке `main` вносятся только через Pull Request.

Перед слиянием Pull Request должен быть проверен другим участником команды. Ревьюер оставляет замечания и предложения по изменениям. Автор Pull Request исправляет принятые замечания отдельными коммитами.

Результаты ревью фиксируются в файле:

`variants/BI-Case/review_log.md`

Для каждого Pull Request в журнале указываются:

- автор изменений;
- ревьюер;
- рабочая ветка;
- целевая ветка;
- замечания ревьюера;
- принято или отклонено замечание;
- выполненные изменения или причина отклонения.

После устранения замечаний и получения одобрения Pull Request сливается в ветку `main`.

## Проверка истории Git после распаковки архива

После распаковки архива необходимо перейти в корневую папку репозитория.

Чтобы убедиться, что каталог `.git` присутствует и репозиторий корректно распознан Git, выполнить:

```bash
git status
```

Если `.git` находится на месте, Git выведет информацию о текущей ветке и состоянии рабочей директории.

Для просмотра полной истории коммитов выполнить:

```bash
git log
```

Для более компактного просмотра истории коммитов:

```bash
git log --oneline
```

Для просмотра истории вместе с ветками, слияниями и тегами:

```bash
git log --graph --oneline --all --decorate
```

Если каталог `.git` отсутствует, команды Git сообщат, что текущая директория не является Git-репозиторием.
